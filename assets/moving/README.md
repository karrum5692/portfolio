# MOVING 부하 테스트

개별 쿼리 최적화가 동시 요청 상황에서도 유효한지 검증하기 위해 작성한 k6 스크립트입니다.

## 설계

실사용 빈도가 높고 쿼리 구조상 부하에 취약할 수 있는 4개 엔드포인트를 고르고, **공지 목록(40건, 가벼운 쿼리)을 대조군으로 추가**했습니다.

판별 기준을 먼저 정하기 위해서입니다. 무거운 쿼리만 느려지면 쿼리 구조 문제이고, 대조군까지 같이 느려지면 인스턴스 한계입니다.

외부 API 호출(AI 예상 견적), 연결 유지형(SSE 알림), 쓰기 작업은 제외했습니다. 각각 실제 과금이 발생하거나, 별도 시나리오가 필요하거나, 데이터를 오염시키기 때문입니다.

## 실행

```bash
k6 run -e BASE_URL=<API_URL> -e TEST_PASSWORD=<시드 계정 비밀번호> load-test.js
```

`STAGE`로 부하 프로파일을 선택합니다. 기본값은 `load`입니다.

| STAGE | VU | 용도 |
|---|---|---|
| `smoke` | 5 | 시나리오가 정상 동작하는지 확인 |
| `load` | 50 | 정상 트래픽 가정 |
| `stress` | 300 | 한계 탐색 |

```bash
k6 run -e BASE_URL=... -e TEST_PASSWORD=... -e STAGE=stress load-test.js
```

## 결과

| 시나리오 | VU | 전체 p95 | 실패율 |
|---|---|---|---|
| smoke | 5 | 102.65ms | 0.00% |
| load | 50 | 74.68ms | 0.00% |
| stress | 300 | 162.51ms | 0.00% |

300 VU · 8분 테스트에서 38,676개 체크를 전부 통과했고, 대조군을 포함한 모든 임계값을 충족했습니다.
